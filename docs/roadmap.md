# agent-repo-kit：七轮迭代与验收计划

版本：1.0｜日期：2026-11-13｜状态：后续实施计划，本文不代表新增能力已经实现。

实施补充：业务仓不要求 GitHub 或任何 CI；本地校验是基础，CI/托管平台仅为可选增强。

目标：将参考仓的成熟工程方式提炼为通用、可安装、可持续维护的仓库工程套件。新仓和存量仓首次接入后，可以继续使用 OpenSpec、其他开发 Skills 或直接与大模型对话；工程要求由仓内规则和可执行校验持续生效。

**一、参照与当前起点**

- 实现仓：[YoloJoel/agent-repo-kit](https://github.com/YoloJoel/agent-repo-kit)，当前实现位于 [PR #1](https://github.com/YoloJoel/agent-repo-kit/pull/1)，核对版本为 `ab65b710bff6dfa9d6f49806b1030aa16fdf802f`，尚未合入 main。
- 参考仓：[YoloJoel/linkdevice-data-service](https://github.com/YoloJoel/linkdevice-data-service)，本计划核对 main 版本 `36bdabc1835f331733e436453bb161bcd913a7b5`。
- 主要参照资产：[工程规范](https://github.com/YoloJoel/linkdevice-data-service/blob/36bdabc1835f331733e436453bb161bcd913a7b5/docs/engineering-standard.md)、[AGENTS.md](https://github.com/YoloJoel/linkdevice-data-service/blob/36bdabc1835f331733e436453bb161bcd913a7b5/AGENTS.md)、[Baseline](https://github.com/YoloJoel/linkdevice-data-service/blob/36bdabc1835f331733e436453bb161bcd913a7b5/docs/baseline/README.md)、[规格校验器](https://github.com/YoloJoel/linkdevice-data-service/blob/36bdabc1835f331733e436453bb161bcd913a7b5/hack/verify_spec.py)和验证报告模板。
- 已有基础：原生 Claude Plugin、三个标准 Skill、自包含初始化助手、仓内执行内核、基础 Baseline/Change/验证/归档、证据时效、有限 Stop 提醒和 CI。已记录 47 项工具测试与七项跨平台/安装器 CI 通过。
- 当前不足：日常开发仍绑定 deliver-change 与 ark.json；专业知识资产、决策管理和专项校验不完整；真实复杂业务仓、真实运行器中的完整效果尚未验收。

本计划保留原完整设计中关于证据、幂等、兼容、风险分级、可恢复与真实验证的要求，并修正其中将 deliver-change 作为日常开发入口的设计。原实现中仍有价值的校验、报告和恢复能力继续复用。

**二、最终产品形态与完成定义**

1. 对用户默认提供 initialize-repo、baseline-repo 两个 Skill；日常开发没有必经的工具包开发 Skill。
2. Claude Code 通过原生 Plugin 安装，其他支持的运行器通过标准 Skills 安装。正常使用无需另装 Python 包、下载工具源码或记忆内部 CLI；已有 Python 运行条件仍需诊断。
3. 首次初始化建立真实项目上下文、工程协议、路径和命令映射、适用检查与运行器接入。新建仓、普通存量仓和已有部分治理资产的仓库分别处理。
4. 使用 OpenSpec 时复用其原生资产与生命周期；其他工具或直接对话开发时，按同一工程标准维护必要资产。统一检查结果，不要求统一操作入口。
5. Baseline、当前 Spec、活动 Change、系统架构、局部 Design、ADR、测试和验证报告各有清晰职责；可从目标和证据追踪到实现与验证。
6. 轻量修改采用轻量流程，功能与高风险修改采用相应资产和验证要求。正常暂停、外部阻塞、规格阶段交付不能被误判为完整实现或强制无限继续。
7. 当前文档和证据随受影响范围维护；保留原始证据与已接受历史；换会话、换 Agent、切换 worktree 可接续。

“达到参考仓”按相同职责的工程资产、实际内容质量和有效校验来验收，不以目录完全相同、文件数量、字数或测试数量判定。只在业务需要时生成对应文档，不为空仓虚构业务、架构或历史。

“超过参考仓”具体指：开发工具更自由、资产维护更少重复、证据与当前版本绑定更明确、变更影响与过期知识更容易发现、多个运行器和工作区可接续、错误完成声明更难混过校验。这不等于承诺模型永不遗漏或所有重构绝对无回归。

**三、总体顺序**

| 迭代 | 主题 | 完成后用户能够观察到的结果 |
| --- | --- | --- |
| IT-01 | 解除开发工具与自有流程绑定 | OpenSpec、其他开发入口和直接对话均可工作，无需 deliver-change 或手写 ark.json |
| IT-02 | 固化专业工程标准与初始化 | 一次接入后有真实项目入口、职责清晰的资产和按风险裁剪的完成标准 |
| IT-03 | 提升 Baseline、契约、DT 与决策质量 | 能阅读文档理解关键业务；事实、缺口、用例和规格晋升有据可查 |
| IT-04 | 补齐工具无关的可执行校验 | 格式、关系、状态、阶段、历史和证据问题能被准确发现 |
| IT-05 | 建立行为保持与目标变化验证 | 缺测试的受影响行为有实施前依据，实施后可运行回归与目标验收 |
| IT-06 | 完成日常无感维护及运行器/CI 接入 | 使用任意已适配开发入口时，提醒、增量检查、接续和合入检查持续生效 |
| IT-07 | 真实仓对标、反例验收与正式发布 | 有实测对标报告、支持矩阵、迁移能力和可以复用的安装使用说明 |

每轮交付更新后的规格、实现、必要验证和执行记录。已存在且不受影响的能力不重做。IT-07 是总体验收；前六轮完成并不自动等于正式达到最终目标。

**IT-01：解除开发工具与自有流程绑定**

目标：将产品职责调整为初始化、知识维护与工程校验，使 OpenSpec 或其他开发工具可以自行编排工作。

实施范围：

- 移除仓内规则中“实现必须使用 deliver-change”的要求；默认安装仅暴露两个用户 Skill，迁移已有安装时保留用户自定义内容。
- 定义工具无关的资产与验证协议：范围、行为变化、需求、设计、任务、验证、状态和证据。工具包内部可以建立可重建视图，不能再形成一套需人工同步的新权威数据。
- 以原生 OpenSpec 为首个适配对象，识别实际版本的原生资产、状态与归档方式。优先复用原生结构化接口和验证能力；不另造 delta 合并器，不用有限解析器宣称完整兼容。
- 其他开发工具支持路径和资产映射；直接对话按风险维护必要文件。允许使用已有编号和组织形式，不强制搬迁文档。
- CI 和本地检查不再只扫描 ark.json；不再要求先调用工具包自己的 change new、activate 或 close 才能被正确验证。
- 当前任务识别优先依据真实差异和明确关联；多个活动工作无法唯一匹配时保留候选和缺口，不能按最近修改时间猜测。
- 对 0.1 已有元数据提供兼容读取与显式迁移方案；保留历史、需求 ID、人工规则和未提交内容。

主要交付物：职责调整 ADR、工具无关协议、OpenSpec 适配层、兼容读取/迁移方案、移除强制入口后的两个 Skill 与仓内规则。

验收：同一类行为变更分别通过原生 OpenSpec、一个其他可用开发入口和直接对话完成；均不调用 deliver-change、不要求手写 ark.json；合法结果通过相同工程检查，缺失必要验证时均不能被判为完整交付。纯文案修改不被升级成完整 Change。

**IT-02：固化专业工程标准与初始化**

目标：把参考仓的工程规范提炼成可配置、按风险裁剪的通用标准。

实施范围：

- 初始化核实项目定位、源码和测试根、模块与进程边界、构建和验证入口、既有规范/设计/CI。能由代码和配置确定的信息自行核对；未知项保留明确状态。
- 生成简洁 AGENTS 入口及适用运行器导入；详细规范独立保存，禁止将所有文档长期塞入启动上下文。
- 明确当前事实、行为承诺、拟议变更、设计和架构决策的不同权威位置；发生冲突时记录并判断，不能直接改写另一方掩盖差异。
- 补齐系统概览、模块说明、契约、DT 用例、Spec、Change、Design、ADR、验证报告和接续记录的专业模板。系统级架构和局部实现设计分工清楚。
- 定义按风险裁剪的资产矩阵：咨询、文案、机械修改、修复、功能、并发/跨模块重构、协议和数据迁移。必要设计与 ADR 的触发条件明确。
- 新仓无历史 Baseline，不虚构产品架构；已有部分资产的仓库复用既有路径、编号、命令和有效规范；已有 Makefile/CI 不被整套替换。
- 工程接入、知识覆盖、业务检查执行、运行器接通、远端门禁分别报告；初始化资产生成完不等于所有层次完成。
- 纳入存量问题与有效例外规则：范围、原因、责任、复核条件和替代验证明确，区分历史问题与新增问题，不能自动降低检查来获得通过。

主要交付物：工程标准、风险/阶段矩阵、完整模板集、配置与路径映射、真实项目上下文、可区分完成维度的初始化报告。

验收：空仓、普通存量仓、已有 AGENTS/OpenSpec/CI 三类接入均通过；重复执行无重复改动，人工内容和脏文件保持；重要约束可从入口定位；不适用项有依据；新仓不会产出虚构的业务结论。

**IT-03：提升 Baseline、契约、DT 与决策质量**

目标：使产物能够帮助人理解代码，并为后续保留行为、形成规格和决策提供可核验证据。

实施范围：

- 除文件盘点外，建立模块/运行模型、端到端业务流程、关键分支、外部边界、状态归属和失败恢复的分析清单。
- 解释输入校验、转换、状态变化、异常传播、副作用、超时、重试、重复、乱序、并发与资源清理；不适用维度说明理由，避免套模板编造内容。
- 对接口、消息、共享数据、文件和配置提取可观察契约，保留格式、错误、时序、恢复及兼容语义，并引用对应版本的源码、配置、测试或运行证据。
- 从已核实行为派生可用于特征测试/契约验证的 DT 场景，记录前置、输入、预期、来源和兼容性判断；观察到的缺陷不能自动变成永久承诺。
- 固化 raw/reviewed/promoted/obsolete 等证据生命周期与需求晋升关系。事实、推断、决策和目标设计分开，原始历史不被当前实现覆盖。
- 维护一份问题/决策源数据，按需要生成清单、决策卡和总览，避免多个文档各自保存冲突状态；已有记录使用映射复用。
- 分开报告文件覆盖、关键行为/契约覆盖、静态核对和实际执行验证。缺少外部旧仓源码时明确未核实，不能把参考文档当作源码验证结果。
- 建立依赖和契约影响关联，更新时提示相关知识需复核；路径/指纹用于线索，语义影响由分析复核。
- 新仓随着代码落地形成当前行为资产；后续修改已存在行为时同样执行基线与回归要求，不能永久以 mode=new 豁免。

主要交付物：强化后的 baseline-repo、完整分析模板、模块/流程/契约示例、DT 场景台账、证据生命周期、问题/决策台账和规格晋升映射。

验收：选定模块仅阅读产物就能理解关键正常/失败流程，并可定位证据；审查不只检查标题和引用。预先列出的重要分支和边界都有解释或明确缺口；源码或契约变化后相关说明能进入复核状态。初始新仓产生业务后再次修改时不得跳过旧行为保障。

**IT-04：补齐工具无关的可执行校验**

目标：覆盖参考仓中可机械判断的规范，同时保留原生工具和不同工程资产的兼容性。

实施范围：

- 在资产归一化视图上检查当前 Spec、delta、Requirement/Scenario、Verification、编号唯一性、退役 ID、重命名和引用关系；对原生工具支持的校验优先复用。
- 补齐 Change、任务、设计触发条件、ADR 状态/替代关系、Baseline 来源/晋升关系、决策与用例关联的检查。
- 按真实 Git 比较基准检查行为、配置、脚本与依赖变化，防止错标 docs、遗漏影响范围和采用过期的轻量声明。
- 保护已有 raw、Accepted ADR 和归档历史；需纠正时建立明确的补充/替代关系。检查策略、运行内核和 CI 自身的变更需要可见审查。
- 支持草案、规格阶段、实现交付、归档等不同阶段要求；规格阶段通过不等于实现交付通过，代码交付不得借阶段声明规避要求。
- 输出带定位和修复建议的统一 Markdown/JSON 报告；正常有效的原生文件不能仅因没有工具包元数据而失败。
- 所需证据绑定被验证内容、策略和执行环境；缺失、失败、部分执行、过期和未运行分别处理。缓存不能把旧结果用于新输入。
- 自动校验仅宣称可确定判断的覆盖，业务说明正确性和测试断言质量由相应审查与行为验证承担。

主要交付物：分阶段检查器、原生适配校验、规范与检查对照表、统一报告、有效例外处理和反例测试。

验收：人为引入缺场景、编号/引用错误、错误归档、未同步规格、过期证据、手写 PASS、越界修改和缺失必需检查等问题时能准确失败；修复后通过；合法 OpenSpec 资产和轻量修改不会被误阻断。

**IT-05：建立行为保持与目标变化验证**

目标：回答“没有 DT，如何知道修改前后兼容”的实际问题，并让测试能发现行为错误。

实施范围：

- 面向受影响范围形成保留行为清单、目标变化清单及对应测试/外部验证，区分有意变化与必须保持的行为。
- 缺测试时，在修改原行为前建立必要的特征测试、契约测试或可复现夹具，并在原始版本实际执行；保存版本、结果和实施前依据。
- 按业务需要覆盖正常、异常、边界、状态、并发、恢复和资源释放，不要求初始化时补齐全仓测试，也不为机械修改制造无意义用例。
- 优先复用项目原生构建、单测、集成和验收命令。首批以参考仓对应的 Java/Maven 和实际选定的存量技术栈验收，其他技术栈通过同一命令/结果协议扩展，不承诺一次支持所有生态。
- 对适合的接口、消息或数据处理场景提供夹具/回放/新旧结果差分接入；时间等非业务变化字段的归一化规则需明确，不能吞掉真实差异。
- 外部系统或旧版本不可运行时，登记缺少条件与替代依据，按约定阶段处理；必需验证缺失时保持 PENDING，不能伪造无回归结论。
- 验证报告关联需求、用例、真实命令和结果，区分保留行为回归与目标行为验收，并显示剩余风险。

主要交付物：基线测试/契约测试接入约定、受影响行为矩阵、原生测试命令适配、可选差分夹具和真实验证证据。

验收：在一个缺少现成测试的场景中先建立并运行旧行为用例，再实施修改；故意破坏需要保留的行为时回归确实失败，有意改变的目标行为按新期望验收。外部验证不可用时不能产生完整交付 PASS。测试数量不能替代这些观察。

**IT-06：完成日常无感维护及运行器/CI 接入**

目标：用户初始化后正常选择开发工具，工程上下文、遗漏反馈、接续和验证持续可用。

实施范围：

- 不同运行器通过薄适配共享规则与检查内核，使用各自真实支持的入口和事件；实施时核对官方接口和实际版本，不照搬其他工具的 JSON。
- 会话启动只给相关规则、活动资产与证据导航，不重做全仓分析；开发期间按差异维护影响状态和所需知识，避免每次工具调用都跑完整构建。
- 日常提示不强制切换开发 Skill，不暗中改写用户目标，不与 OpenSpec 等原生工作流反复嵌套。
- 准备交付时检查对应阶段；正常结束一轮对话、用户暂停、外部阻塞与完整交付分别处理。有限提醒/补救，保留可接续状态，不形成 Stop 死循环。
- 无专用活动 Change 指针时仍可依据差异和原生资产给出反馈；多个工作并存时不猜测归属。保留 worktree/分支/会话隔离。
- CI 使用实际 PR 基准重新检查并运行必需命令，保留可追查产物。已有流水线增量接入；PR 模板、评审责任和所需远端门禁形成明确的配置与诊断项。
- 明确区分规则生成、原生加载、Hook 触发、命令执行、有效阻断和远端必需检查。执行远端设置需要相应已有授权和权限，未落实时保持未验证状态。
- 完成 Claude Code、Codex 的真实环境验证；OpenCode 若完成原生适配和实测则纳入相应支持等级，否则明确标注已验证的基础范围。不能以协议测试替代真实运行器验收。

主要交付物：运行器适配、增量上下文与影响维护、稳定接续记录、轻量本地反馈、CI/评审集成和分层支持矩阵。

验收：初始化后分别使用已适配 OpenSpec 流程、其他开发入口和直接对话，均无需调用工具包日常 Skill；遗漏必要材料或验证时有对应反馈，CI 可发现问题。切换会话/运行器可恢复真实进度；两个 worktree 不串扰；无关咨询和正常暂停不会被强制阻断。

**IT-07：真实仓对标、反例验收与正式发布**

目标：把“已经实现”升级为“在真实使用中达到对标效果”。

实施范围：

- 建立参考仓资产—通用要求—实现能力—验收证据的对照表，覆盖入口、规范、架构、Baseline、DT、决策、Spec、Change、测试、报告和 CI。
- 使用一个有真实需求的新建项目完成首个完整能力交付；使用至少一个可访问实际源码和构建条件的真实存量仓完成接入及一个有意义的行为修改/重构。小型工具夹具只能作补充。
- 对已有 AGENTS/OpenSpec/manual/CI 的项目验证复用能力；不直接修改参考仓的主干。只有文档、缺少旧仓源码的范围按资料接入验收，不能冒称完成源码取证。
- 端到端覆盖原生 OpenSpec 的建立、实施、验证、规格同步和归档；其他已适配开发入口和直接对话也执行同一工程标准。
- 运行故意破坏行为、过期报告、缺失外部检查、规格脱节、任务未完成、错误资产映射等负向验收；记录发现问题、修复与复验结果。
- 完成已初始化 0.1 仓的显式升级、人工定制冲突、重复升级和失败恢复。正常升级只影响管理范围，不重编号或删除有效历史；新安装无需旧的源码 bootstrap/pip 路径。
- 对宣称支持的主要操作系统与运行器分别记录版本及真实结果；打包的两个 Skill、Plugin、文档与内核保持一致。
- 输出面向用户的新仓、存量仓、已有 OpenSpec 三条使用说明，以及排障、升级、接续和边界说明。开发工具保持可选，用户不需要背内部命令。

主要交付物：真实案例仓/变更、参考仓对标报告、正反验收证据、正式支持矩阵、迁移与恢复能力、原生发行包和使用说明。

验收：下面的验收矩阵完成且证据可复查，才能宣称达到本计划目标。某运行器、技术栈或环境未实测，则仅按实际验证范围发布，不能统称全支持。

**四、最终验收矩阵**

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| AC-01 | 空仓接入 | 有真实可用规则与验证入口；没有虚构历史、业务和架构 |
| AC-02 | 普通存量仓接入 | 有可读模块/流程/契约、证据、覆盖、DT 场景和明确缺口 |
| AC-03 | 已有部分治理资产 | 原规则、原编号、设计、CI、人工内容和脏文件保留，无重复体系 |
| AC-04 | 原生 OpenSpec 开发 | 可完成原生流程及归档，无需 deliver-change、手写 ark.json 或第二套生命周期 |
| AC-05 | 其他入口/直接对话 | 按同一要求维护适用资产和验证，入口自由，不被暗中切换 |
| AC-06 | 轻量修改 | 不要求完整 Change、全仓 Baseline 或新测试；相关检查仍执行 |
| AC-07 | 无 DT 的行为修改 | 实施前旧行为用例实际执行；实施后回归与目标验收分开，负向破坏能被发现 |
| AC-08 | 新仓持续演进 | 首次业务落地后再修改时，已有行为同样得到基线与回归保障 |
| AC-09 | 规格和设计一致性 | 合法原生资产通过；缺场景、错误关联、漏设计/决策等适用问题被发现 |
| AC-10 | 证据过期或手写通过 | 旧版本、部分执行、伪造完成声明不能当成当前完整交付证据 |
| AC-11 | 外部环境不可用 | 明确 NOT_RUN/PENDING 与缺少条件，未完成的必需验证不汇总为 PASS |
| AC-12 | 受影响知识维护 | 相关说明进入复核并更新；历史 raw 保持；规格晋升与决策关联可查 |
| AC-13 | 规格阶段与完整交付 | 阶段性检查和实现完成分开；不能用规格阶段声明放行缺验证的实现 |
| AC-14 | 换会话/运行器 | 能从仓内记录及真实差异恢复目标、范围、结果和下一步 |
| AC-15 | 多 worktree/多任务 | 上下文和证据不串扰，歧义不靠最近时间猜测 |
| AC-16 | Hook 暂停与故障 | 有限反馈、正常交接；配置存在不会被当成已加载或可信执行 |
| AC-17 | CI 与远端门禁 | 实际候选版本重新验证；required checks 和保护状态如实记录 |
| AC-18 | 升级与恢复 | 自定义内容及历史保留，冲突可定位，失败恢复不重置整仓 |

每条验收记录至少包含：仓库与范围、提交及工作区状态、运行器/工具版本、使用的开发入口、实际操作、产物位置、检查结果、负向检查（适用时）和限制。一个 PASS 结论不得覆盖其他未运行场景。

**五、与参考仓的对应及改进**

| 参考仓的成熟能力 | 对应迭代 | 通用化后的改进方向 |
| --- | --- | --- |
| AGENTS 入口、资产分工、风险分级 | IT-01、IT-02 | 不绑定开发 Skill；已有结构可映射，减少提示负担 |
| 架构、设计、ADR、差异与决策记录 | IT-02、IT-03 | 按适用范围生成；一份决策源数据维护多个阅读视图 |
| raw、模块、契约、DT、规格晋升 | IT-03 | 源码/工作区证据与当前知识绑定，增量提示复核 |
| Spec/Change/ADR/Baseline 专项校验 | IT-04 | 原生适配、分阶段校验、反例验证及明确错误定位 |
| 测试追溯与验证报告 | IT-04、IT-05 | 保留行为与目标变化分开，真实执行及过期证据更明确 |
| 工程命令、CI、评审与交付 | IT-05、IT-06 | 复用不同技术栈入口，跨运行器共用检查，按真实差异验证 |
| 成熟仓持续积累的效果 | IT-07 | 用真实新仓/存量仓和负向场景证明，避免只展示模板 |

**六、执行约束**

- 七轮是后续实施顺序，不是已经完成的功能清单，不承诺未经执行验证的工期或覆盖率。
- 每轮围绕具体可观察行为交付，不以“多加模板、改了文档、测试数量增加”作为完成条件。
- 公共规则、模板、检查和运行器适配分层；不复制多套规格引擎，不引入必需常驻服务、MCP 或自动多 Agent 编排。
- 工具版本与官方接口在实施对应适配时核实；本计划不把当前版本的能力假定为长期不变。
- 用户通常只需要初始化一次并给出后续任务。新的重要业务/兼容性取舍、必需外部条件和未授权的远端操作仍需具体决策；普通事实和常规实现选择由 Agent 处理。
- 实施进度以 docs/iterations/ 和各迭代 PR 的实际验证与合入结果为准。
