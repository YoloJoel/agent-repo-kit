# 0.4.0-rc.1 本地试用

试用目标是初始化一次，之后用普通提示词、OpenSpec 或 Superpowers 开发，仓库能持续执行同一套 Spec、Design、ADR 和验证约定。候选分支为 `codex/workflow-contract-pilot`。正式主线、候选、业务仓内已复制的检查内核各有自己的版本。

## 迭代与验收

| 轮次 | 交付及验收 |
| --- | --- |
| 1 · 交付判定 | 同一个新增行为，分别缺 delta、Design 和必需 ADR 时能定位缺口；已有 Accepted ADR 可复用，恢复已承诺行为可引用已有需求。 |
| 2 · 跨入口衔接 | OpenSpec、普通对话或 Superpowers 产物沿用同一个 Change。已有设计与计划可直接写入或引用；引用源缺失、计划未完成能被发现。 |
| 3 · 候选版与私有仓试用 | 测安装、显式升级、重复升级、原生归档和回归反例。第一轮优先选一个代表性的小需求；先用你平常的入口，结果良好再交叉复验。 |
| 4 · 收到摘要后 | 将观察到的漏放、误拦、接力失败变成公开合成反例，修复后重跑。随后推进新产品、原地存量、跨仓重写三类接入盲测，用独立事实和决定验证来源、受影响消费者和未决项。 |

## 更新候选

在业务仓之外取得工具仓副本。按交付回复给出的完整提交固定候选；`git rev-parse HEAD` 应对应同一提交。先在业务仓的临时分支或 worktree 操作，保留人工规则及原有修改。

```sh
git clone --branch codex/workflow-contract-pilot https://github.com/YoloJoel/agent-repo-kit.git agent-repo-kit-pilot
```

- Claude Code：在业务仓目录运行 `claude --plugin-dir <候选工具仓绝对路径>`，调用 `/agent-repo-kit:initialize-repo`。若宿主显示同名插件，确认此次加载的是候选目录。
- Codex：在业务仓目录按现有安装方式从候选目录加载两个 Skills，例如 `npx skills@1.8.1 add "<候选工具仓绝对路径>" --skill "*" -a codex -y`，再启动新会话并调用 `$initialize-repo`。OpenCode 可使用相同安装方式，把 agent 改为 `opencode`。
- 给初始化 Agent 的要求：“这是本地试用。在这个工作副本接入候选版本；已接入过就显式升级（安装助手 --upgrade）。复用已有项目规则和编号，把适用的 Spec/Design/ADR 触发条件映射到 policy.artifact_rules；完成项目入口和配置复核，分别报告接入状态和实际业务测试。” 若只想先试一个能力，可明确限定范围，并保留其余范围的真实状态。
- 在业务仓核对 `python hack/ai/ark.py --version`，预期 `0.4.0-rc.1`。需要进一步核对时，在本地比较候选目录的 `skills/initialize-repo/scripts/engine.py` 和业务仓的 `hack/ai/ark.py` 的 SHA-256；不需要回传这两个值。

## 如何避免评价提示本身替工具补规则

先在一个全新开发会话，仅用正常业务措辞提出一个真实、可回退的小需求，优先选项目自身约定确实涉及契约或持久化模型的任务。输入只写目标、业务验收和原有约束，用日常所选入口执行。可用预先约定的测试数据。开发会话结束后，另开一个只读评价会话，贴下面的提示词。想对比三个入口时，从同一已初始化提交派生独立副本，以同一业务需求重复；或选一次中途换入口的接续，分别标记观察范围。

## 本地评价提示词（复制到新的会话）

你是本地仓库的只读评审。只在本地查看当前试用的 diff、权威工程规则、有效 Spec、活动 Change、已接受的 ADR、测试断言和实际执行记录。保持被评估的交付现场，不要替开发会话补文档、补实现或修复缺口。若需要做反例，在独立临时副本执行。缺命令、缺授权、缺外部依赖时报告“未测”及原因类别。

1. 核对实际内核版本、初始化/升级方式、此次开发入口及任务类型。先从本仓原始约定和业务需求独立推导它应当补哪些资产，哪些已有资产可以复用。
2. 检查开发会话在没有额外提醒时实际完成了什么。分别评价变更分类、Spec 的可观察场景、Design/ADR 的触发与依据、测试对关键边界是否真有断言、报告是否区分真实执行和阶段性完成。检查人工内容、历史编号和已有决策是否保留。
3. 查看仓内 check 对实际差异的结论，与独立判断对照。若有合适的临时副本，移去一项本来必需的资产，或把被引用计划中的已完成任务改为未完成，重跑同一检查；说明是否准确定位。已有失败或环境缺失要标明，避免把它当成反例命中。
4. 如实际换过入口，检查能否沿用同一 Change 和有效规格。记录多生成一套文档、误拦轻量修改、漏掉消费者或仍需用户提醒的情况。没有运行过的入口一律记“未测”。
5. 最终只输出以下可粘贴的脱敏摘要，不超过 600 字。保留原始证据在本机，不向外发送。将仓名、模块、接口、需求和依赖用 A/B/C 等代号替代；省略源码、原文、业务值、路径、命令参数、日志、人员、内网地址和密钥。只保留公开的工具版本、通用检查名和结果。遇到不确定是否敏感的字段，概括成类型。

- 候选版本 / 运行器 / 实测入口 / 新仓、存量或重写
- 任务类型 / 初始化或升级 / 接入范围
- 项目原本要求 / 实际交付 / 需要人工提醒的次数
- 本地检查结果 / 真实业务测试结果 / 未测范围
- 负例预期与实测 / 是否正确指出缺项
- 发现最多三项：漏放、误拦或接续问题；每项给出“最小触发条件 → 预期 → 实际 → 影响”
- 建议：扩大试用、修复后复测或暂停，以及首要原因
