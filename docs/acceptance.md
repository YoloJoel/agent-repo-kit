## 与参考仓的对应

| 工程职责 | 0.2.0 实现与验收 | 边界 |
| --- | --- | --- |
| 入口与工程规范 | 简洁入口、真实上下文、风险与阶段要求，复用既有规范 | 不虚构产品或完整架构 |
| Baseline / 契约 / DT | 流程、状态、失败、来源、用例、缺口，独立静态/执行状态 | 原文或函数索引不自动成为语义认证 |
| Spec / Change / Design / ADR | 原生布局、既有 ID/标题、重命名/退役、引用/状态检查 | 原生工具负责同步/归档；语义仍需审阅 |
| 决策与历史 | 单一台账来源、衍生视图、晋升记录和不可改写原始证据 | 原生 Markdown 台账由原流程维护，不自动转换 |
| 测试与交付 | 实施前实际执行、稳定夹具、保留回归/目标验收、部分/过期证据检查 | 断言质量和场景完整性不由编号匹配证明 |
| 日常维护 | 按差异关联、受影响知识、接续、有限反馈、换 worktree 隔离 | 歧义不猜测；普通暂停不强制交付 |
| 执行入口 | 本地检查、可选 Git Hook、其他流水线接入 | 不要求 GitHub、远端或 CI |
| 分发与升级 | 两个 Skill、自包含助手、原生 Plugin、显式 0.1 升级 | 宿主信任不被绕过，人工冲突不被强改 |

相较固定业务仓，已验证的改进是开发工具自由、跨仓路径复用、原始执行依据与当前验证区分、明确的过期/部分执行反馈，
以及没有 CI 时仍有可执行的本地检查。不能把这解释为“所有运行器、所有业务自动达到参考仓内容质量”。
