# 0.2.4 项目入口与规格内容质量修复

本地验证完成；发布与最终 CI 见对应 PR。此报告不宣称对所有仓或内部源码的普遍等价。

## 修复

- AGENTS 改为项目定位/技术栈、架构约束、资产、模块边界、实际命令、开发流程、优先级七段入口。
  来源事实由 Agent 从实际项目整理，脚本安全刷新并保留人工/原生入口；不再把构建清单拼在入口里。
- 从实际生产/配置/构建来源建立主要能力映射；未读或未覆盖的业务范围明确 PARTIAL/PENDING。
  支撑、生成和 vendor 排除需理由；少数生命周期规格不能代表整个仓。
- Spec 正文需独立说明输入、规则、结果/副作用、异常、阈值/单位/默认值和场景。
  Baseline/Source 是依据；精确跨规格复用需已有当前 owner。新增窄范围引用正文、缺失 owner 和
  重复通用 Purpose 检查，不能把这些检查说成理解了全部语义。
- 源码审计必查项目入口、主要能力遗漏以及隐藏 Baseline 后 spec 是否仍可验收，并覆盖实际产物。
- onboarding-status 汇总当前质量与范围；初始化报告带阶段与时间，不与后续编译或测试混作同一结论。

## 实际内容验收

工具源码/最终安装包各 140 项测试通过，原生资源与两个 Skill 格式通过。
实测对象为原始 cachetools 源码快照及其 416 项原测试，不是预写好的规格，也不是几行代码。
产物包括中文七段入口、六类业务能力和十条需求、模块/契约/案例及能力映射；26 个原始输入未改。
这些数字只说明范围，实际审阅还覆盖 TTL/TLRU 单位/等号边界/副作用、容量计量、淘汰次序、键语义、
同步/统计、描述符及便利装饰器共享状态等可观察规则。

初次独立审计发现并修正四类内容问题；父审阅后又发现重复 Purpose 和遗漏的具体错误类型，
后续源码复核修复并收窄跨版本异常承诺。保留该过程，不宣称第一轮即没有问题。
最终父复验使用与源码/原生/安装包一致的内核，实际 unit 命令执行 416 项通过、输入指纹未变化。
覆盖、规格和审计 PASS；总体仍 PARTIAL/PENDING，因为发布构建、typing、跨版本及 Hook 条件未验证。
不把编译、映射或静态审计当作完整业务运行证明。

实际工件、命令、哈希、限制与复核输出见 [artifact-quality-use.json](../evidence/artifact-quality-use.json)。

无需删除已有 Baseline/spec；Agent 应据源代码补全入口、主要能力覆盖与规格正文，再做源码复核。
