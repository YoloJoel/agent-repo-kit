# 使用方式

安装一次 Plugin 或标准 Skills，每个业务仓调用一次 initialize-repo。以后直接描述需求，
继续使用 OpenSpec、其他开发 Skills 或直接对话。工程规则、上下文、知识记录和检查内核留在仓内。
需要 Python 3.11+；正常使用不需要额外安装 Python 包、全局 ark、MCP 或常驻服务。

## 新建仓库

1. 在空仓调用 initialize-repo，说明真实项目目标。Agent 建立工程入口、上下文、验证命令和适用规则。
2. 首次开发按实际需求形成规格、代码和测试。没有历史系统时不编造 Baseline、架构或业务结论。
3. 首次交付运行真实项目命令，记录结果。形成既有行为后，后续修改同样需要实施前依据、保留行为回归和目标验收。

可以直接说：“实现事件日志，重复事件不得多写，冲突必须报错。”不需要再指定工具包的开发 Skill。
`examples/event-journal` 和 OpenSpec 验收脚本演示了首次交付、第二次扩展、归档和故意破坏回归。
它是单写入者演示，不是生产级 WAL 或多实例保证。

## 普通存量仓库

1. 调用 initialize-repo。Agent 先核对源码、构建、已有规范和脏文件，再接入规则。
2. Agent 使用 baseline-repo 整理实际职责、业务流程、状态、失败处理、契约、用例、证据和缺口。
   大仓按模块推进并保存接续；盘点完成不代表全仓理解或运行验证完成。
3. 日常只补齐受影响范围。缺少 DT 时，先在原版本实际运行必要的特征/契约用例，再修改实现。
4. 交付分别查看保留行为回归和目标行为验收。缺少环境、外部检查、有效证据时保留 PENDING。

不要求初始化时补齐全仓测试，不用目录数量或测试数量替代行为覆盖审查。

## 已有 OpenSpec / AGENTS / manual / CI

直接要求：“接入本仓，复用已有路径、编号、规范和验证入口，保留人工修改。”
Agent 在首次写入前映射必要路径，继续使用原生资产和原生同步/归档，不建立第二套生命周期。
严格的 raw 批次格式可把机器证据映射到独立位置；原验证报告模板和 YAML front matter 继续生效。
已有决策台账保持原格式；自动写入器不应另建竞争性的 JSON 来源。

日常开发可以使用 `/opsx:...` 或其他已安装工具，也可以直接与模型对话。工具包只提供共同工程要求和检查。
多个工作范围重叠时，根据真实文件关联澄清归属；不按最近时间猜测，也不要求全局活动指针。

## 没有 GitHub / 没有 CI

GitLab、Gitee、内部 Git 或本地目录均可使用。本地检查是基础；默认不会生成 GitHub Actions。
由 Agent 在交付前运行仓内检查。可选的本地 pre-commit 检查会执行同一入口，保留已有 Hook 管理器。
已有流水线可以增量接入相同命令；远端必需检查和保护规则需要另外落实，配置文件存在不代表门禁生效。

运行器首次加载项目 Hook 所需的审阅/信任由宿主管理；套件不会绕过。Claude 原生安装、启动事件，
标准 Skills 安装、本地 Git 阻断和跨平台命令已经分别验证。Codex 可信 Hook 加载、完整模型会话中的
Stop 行为，以及 OpenCode 生命周期仍按未实测范围记录，见 [支持矩阵](compatibility.md)。

## 暂停、接续、升级

正常暂停保存完成项、真实结果和下一步；外部阻塞明确记录条件。新会话读取上下文、实际差异和 checkpoint。
不会因为结束一轮对话就强制把整个 Change 做完，也不会无限重复 Stop。

升级时更新已安装的 Plugin/Skills，再明确要求 initialize-repo 执行升级。仅替换可确认未被人工改动的管理文件；
人工冲突保留并明确报出。旧版未定制的 deliver-change 副本会退役；定制副本保留并记录为用户维护。
原始证据、Accepted ADR、归档历史和既有编号保持。失败恢复仅处理本轮触及的文件。

Agent 需要的操作细节见 [CLI](cli.md) 和 [本地集成](local-operation.md)，用户无需背这些命令。
